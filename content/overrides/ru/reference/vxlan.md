# VXLAN-хаб: настройка и выход в сеть

VXLAN-хаб соединяет игровую сеть коннекторов с вашим компьютером по UDP, как будто гость включён в обычный Ethernet-кабель вашей машины. С ПК можно ходить в гостя (ping, `nc`, `ssh`, если в госте есть `sshd`), а при желании выпустить гостя в обычный интернет через ПК.

## Как это устроено

```
гость ── коннектор ── VXLAN-хаб ══ UDP :4789 ══ ядро Linux ПК (vx0) ── ПК ── интернет
        (сеть в игре)            (туннель)       (интерфейс VXLAN)
```

- Туннель работает на уровне Ethernet (L2): кадры гостя доходят до интерфейса `vx0` на ПК без изменений. Адреса, ARP, маршруты настраиваете вы.
- На сервере **один туннель и один удалённый узел** (`remoteHost`). У каждого хаба свой случайный **VNI** (номер сети). Кадры с чужим VNI игнорируются.
- Сервер принимает датаграммы только с IP-адреса `remoteHost`, с любого порта: ядро Linux выбирает исходящий порт само. Ответы сервер шлёт на `remoteHost:remotePort`.
- Шифрования нет. VNI не пароль.

## 1. Сервер Minecraft

В `config/oc2r-common.toml`, раздел `[vxlan]`:

```toml
[vxlan]
  enable = true
  remoteHost = "203.0.113.10"   # адрес вашего ПК, каким его видит сервер
  remotePort = 4789             # порт, который слушает ПК
  bindHost = "0.0.0.0"
  bindPort = 4789               # порт сервера; на нём ждёт туннель
```

Конфиг читается при старте, поэтому перезапустите сервер. Откройте UDP `bindPort` на сервере для адреса ПК (файрвол хостинга тоже).

Поставьте VXLAN-хаб рядом с сетевыми устройствами (коннекторами или другими блоками сети; к шине устройств он не подключается). **Правый клик по хабу пустой рукой** показывает его VNI и готовую команду для ПК. Тот же номер пишется в журнал сервера: `VXLAN hub at … uses VNI …`.

## 2. ПК (Linux, нужен root)

```sh
VNI=<номер с хаба>
ip link add vx0 type vxlan id $VNI dstport 4789 remote <адрес-сервера> local <адрес-ПК>
ip link set vx0 mtu 1450
ip addr add 10.77.0.1/24 dev vx0
ip link set vx0 up
```

`dstport` — порт, на котором ПК слушает; он должен совпадать с `remotePort` в конфиге сервера. `mtu 1450` оставляет место под 50 байт заголовков VXLAN при обычном 1500 в сети.

Файрвол ПК должен пускать UDP 4789 от адреса сервера, например:

```sh
nft add table inet vx
nft "add chain inet vx in { type filter hook input priority 0 ; }"
nft add rule inet vx in ip saddr <адрес-сервера> udp dport 4789 accept
```

(так правило добавляется к существующей политике; если у вас `ufw` или `firewalld`, откройте порт там). Если ПК за домашним роутером, нужен проброс UDP 4789 на ПК; удобнее соединить сервер и ПК через VPN (WireGuard, Tailscale) и использовать VPN-адреса как `remoteHost` и `local`. Динамический адрес ПК не подходит: `remoteHost` фиксированный.

Windows и macOS не умеют VXLAN встроенными средствами: используйте Linux в виртуальной машине или WSL2 с мостовой сетью.

## 3. Гость

Назначьте гостю адрес из той же сети, что `vx0`. Для гостевого Linux:

```sh
ip addr add 10.77.0.2/24 dev eth0
ip link set eth0 up
ping 10.77.0.1
```

Для OnyxOS: `netcfg list`, затем `netcfg set <индекс> 10.77.0.2 255.255.255.0 0.0.0.0 0.0.0.0` (шлюз и DNS при выходе в интернет см. ниже). С ПК: `ping 10.77.0.2`. Если в госте работает сервер TCP, ПК достучится до него через туннель: `ssh user@10.77.0.2` сработает для гостя с `sshd`. В штатной OnyxOS `sshd` нет.

## 4. Выход гостя в обычный интернет

**Способ A, проще всего: Internet Card или Internet Gateway.** Они выходят в интернет прямо с сервера и не требуют ни VXLAN, ни настройки ПК. Включите `internetCardEnabled` в разделе `internet_card` и поставьте Internet Card в компьютер или Internet Gateway в сеть. Подробности в статье [Сетевой стек](/ru/reference/networking).

**Способ B: через ПК как маршрутизатор.** Нужен, если гость должен быть в вашей локальной сети или выходить в интернет с адреса ПК. На ПК:

```sh
sysctl -w net.ipv4.ip_forward=1
nft add table ip nat
nft "add chain ip nat post { type nat hook postrouting priority 100 ; }"
nft add rule ip nat post ip saddr 10.77.0.0/24 oifname "<внешний-интерфейс>" masquerade
nft add table inet fw
nft "add chain inet fw fwd { type filter hook forward priority 0 ; }"
nft add rule inet fw fwd iifname "vx0" accept
nft add rule inet fw fwd oifname "vx0" ct state established,related accept
```

В госте шлюз — адрес ПК на `vx0`, DNS — любой доступный:

```sh
ip route add default via 10.77.0.1
echo "nameserver 1.1.1.1" > /etc/resolv.conf
ping 1.1.1.1
```

В OnyxOS: `netcfg set <индекс> 10.77.0.2 255.255.255.0 10.77.0.1 1.1.1.1`. Здесь маршрутизация и NAT — стандартная настройка Linux; через туннель проверены ARP и `ping` между ядром Linux и хабом, сам выход гостя в интернет этим способом отдельно не проверялся.

Не включайте на хабе одновременно Internet Card и маршрут по умолчанию через ПК, если не понимаете, какой путь выберет гость: у гостя должен быть один шлюз по умолчанию.

## Проверка и диагностика

На ПК: `ip -s link show vx0`, `ip neigh show dev vx0`, `tcpdump -ni any udp port 4789`. На сервере смотрите журнал: `VXLAN hub at … uses VNI …`.

| Симптом | Причина |
|---|---|
| `ping` гостя: `Destination Host Unreachable`, в `tcpdump` кадры уходят, ответов нет | VNI на ПК не совпадает с хабом; `enable = false`; сервер не перезапущен; адрес гостя не из сети `vx0` |
| `tcpdump` на ПК не видит ответов сервера | неверные `remoteHost`/`remotePort`; файрвол ПК или роутера блокирует UDP 4789 |
| Кадры не доходят до сервера | файрвол сервера не пускает UDP `bindPort`; `remoteHost` — не тот адрес, с которого реально приходят пакеты (NAT) |
| Работает ping, но большие передачи виснут | MTU: задайте на `vx0` 1450 и не больше в госте |
| Предупреждение «dropped inbound frames» в журнале | поток кадров больше очереди; увеличьте `packetQueueCapacity` |

## Безопасность

- Кадры туннеля не шифруются и не подписываются. Не открывайте порт в интернет всем подряд: разрешите UDP только с адреса ПК/сервера. Для публичных сетей оборачивайте туннель в VPN.
- Хаб принимает кадры с любого порта адреса `remoteHost`; защита — адрес и случайный VNI.
- Через ПК как маршрутизатор гость получает доступ ко всему, что видит ПК. Ограничьте это правилами `forward`.
